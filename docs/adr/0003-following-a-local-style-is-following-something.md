# 0003, following a local style is following something

## Status

Accepted, after a real file demonstrated the previous rule was wrong.

## Context

A layer was treated as tokenised when a variable was bound to it, or when it
pointed at a style whose `remote` flag was true. `remote` means the style lives
in another file, which is the only signal the plugin API offers that a style
came from a published library.

The reasoning was that a style nobody published is a scratch value rather than
a design token, so it should not count.

Then the auditor was pointed at a real file for the first time: 26,966 nodes,
355 styles, 267 variables, none of them published, because the file is a
product design file and not a library. Publishing a library needs a paid Figma
plan, which most files do not have behind them.

It reported 14,638 findings. Of the 11,654 typography findings, **10,466 were
text layers correctly using a text style**, flagged for the single reason that
the file was not itself a library. Another 90 paint findings were the same
mistake. The tool told a well organised file it was almost entirely broken.

A designer uninstalls that in thirty seconds, and they would be right to.

## Decision

A layer is tokenised when it follows anything: a bound variable, or a style
that exists in the file. Published or not.

The question the old rule was really asking, how much of what this file follows
comes from a library, is a genuine question and a different one. It is reported
as `libraryAdoption`, alongside the drift numbers and worth no severity,
because a single file design system is a legitimate thing to have rather than a
defect.

A style id that resolves to nothing is still drift. It follows a style that is
not there, which is worse than following nothing.

## Consequences

On the same real file, without touching anything else: 14,638 findings became
3,598, and typography findings fell from 11,654 to 1,188. Roughly three
quarters of the output was noise generated by one rule.

The cost is that the tool can no longer tell a design token from a swatch
somebody saved once, in a file with no library behind it. That distinction is
not available from the API in that situation, and the previous rule was not
recovering it either. It was only guessing, at enormous cost.

Two fixture cases changed from labelled drift to deliberately unlabelled, and
`fixtures/recorded/drift-01/labels.json` records why in its notes. The label
was following a rule that has since been rejected on evidence, which is the
only circumstance in which a label should be edited after the fact.
